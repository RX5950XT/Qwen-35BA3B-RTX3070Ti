# 35B MoE 本地推理優化與調優實驗報告 (綜合版)

本報告整合了本專案在 **RTX 3070 Ti (8GB VRAM) + 64GB/64GB RAM** 硬體邊界下，歷經多輪「參數設定 - 自動化測量 - 數據分析 - 參數調整」往復閉環實驗所獲得的核心數據、物理學規律、記憶體單/雙通道對比以及技術結論。

---

## 1. 硬體規格與記憶體通道升級對比

LLM 的新字生成階段 (Decode Phase) 是典型的 **記憶體頻寬受限 (Memory-Bound)** 任務。生成每個 Token 時，CPU/GPU 必須從記憶體載入模型參數。因此，記憶體頻寬直接決定了推論速度的物理鐵壁。

### 1.1 記憶體頻寬實測數據對比
本專案經歷了記憶體配置的關鍵升級，實測頻寬（使用多進程 NumPy 壓測）對比如下：

| 記憶體配置時期 | 物理插槽規格 | 實測唯讀頻寬 | 實測複製頻寬 (Copy BW) | 理論極限與通道狀態 |
| :--- | :--- | :--- | :--- | :--- |
| **單通道時期** (舊配置) | `8G+16G+16G+32G` 混插 | `6.03 GB/s` | **`18.48 GB/s`** | 退化至 **Flex Mode 非對稱單通道**，時序放寬，定址遲滯。 |
| **雙通道時期** (新配置) | `32G+32G` 對稱插槽 | **`33.46 GB/s`** | **`43.20 GB/s`** | 成功解鎖 **標準對稱雙通道 (DDR4-3200)**，複製頻寬飆升 **133.8%** (唯讀頻寬大增 `454.9%`)！ |

### 1.2 單通道與雙通道下的推論 TPS 演進
記憶體頻寬的大幅提升直接體現於模型實測的解碼生成速度（TPS，註：表中除明確標記為「理論值/預期」外，所有單雙通道之頻寬與 TPS 數據，均為在該實體硬體上實際運行壓測所得出的真實測量數據。其中 TPS 為經網格壓測調優後的「最優最快極限 TPS」）：


| 模型名稱 (35B MoE) | 量化格式 | 單通道 (18.48 GB/s) 峰值 TPS | 雙通道 (33.46 GB/s) 尋優極限 TPS | 性能增幅與調優特徵 |
| :--- | :--- | :--- | :--- | :--- |
| **Qwen3.6-35B** (MTP) | **Q4_K_M** | `29.26 t/s` | **`35.02 t/s`** | 🚀 提升 19.7%！啟用 `f16` KV cache 並卸載 5 層專家至 GPU。 |
| **Qwen3.6-35B** (MTP) | **Q3_K_M** | `29.09 t/s` | **`30.65 t/s`** | 🚀 提升 5.4%！啟用 `q8_0` KV cache 並卸載 5 層專家。 |
| **Ornith-1.0** (無MTP) | **Q4_K_M** | `27.43 t/s` | **`27.43 t/s`** | 受限於 CPU 反量化算力瓶頸，純 CPU 解壓縮速度觸牆。 |
| **Ornith-1.0** (無MTP) | **IQ3_M** | `22.29 t/s` | **`22.29 t/s`** | 受限於 imatrix CPU 計算開銷，高頻寬未能完全釋放。 |

> [!TIP]
> **💡 為什麼 Q4 最優配置選 `f16` KV 快取，Q3 卻選 `q8_0`？**
> *   **Q4_K_M**：32K 內顯存充足，使用 **`f16`** 可以**完全免去** KV 快取在讀寫時的解壓反量化計算開銷，從而榨出最高的 **`35.02 TPS`** 物理極限。
> *   **Q3_K_M**：因為 3-bit 權重在 CPU 端的反量化計算開銷（算力牆）顯著大於 4-bit，此時推論速度完全被 CPU 計算鎖死。經壓測，在此狀態下使用 `f16` 與 `q8_0` 的 TPS 完全相同，故調優策略選擇 **`q8_0`**，在不犧牲速度的前提下，為主機省下近一半的顯存空間。

## 2. 核心架構決策與 CPU-GPU 數據流

對於 35B MoE（350B 總參數，每 Token 激活 3B），當 VRAM（8GB）不足以完全容納模型時，必須使用 **CPU-GPU 異構混合推理**。

### 2.1 異構混合計算數據流
當我們在命令行設定 `--override-tensor "ffn_.*_exps.*=CPU"` 時：
1. **GPU VRAM**：載入所有 Dense 注意力層 (約 3.0GB) 與 KV Cache (如 32K f16 為 2.56GB)。
2. **系統 RAM**：載入所有 256 個 MoE 專家。
3. **數據流向**：GPU 計算完 Attention 後，將僅有 **幾十 KB 的特徵向量** 經由 PCIe 傳送至 CPU，CPU 尋址並從系統記憶體中載入該層激活的 2 個專家參數進行計算，計算完後再將幾十 KB 的特徵向量送回 GPU 進行下一層循環。
4. **結論**：PCIe 頻寬完全不是瓶頸。**唯一的瓶頸在於記憶體搬運專家權重至 CPU 的速度，這完美解釋了為什麼記憶體雙通道能大幅提速！**

### 2.2 GPU MoE 專家卸載最佳化 (打破 CPU 反量化鐵壁)
即使在雙通道 (33.46 GB/s) 下，純 CPU 處理專家運算也會遭遇 **CPU 反量化運算算力牆 (CPU Bound)**。
* **破局點**：我們設定 `-ncmoe 35`，將 41 層中的 5 層 MoE 專家（約 2.5GB 顯存）卸載至 GPU VRAM，利用 GPU Tensor Cores 的強大矩陣算力直接抹平這 5 層的反量化延遲。
* **显存安全邊界**：3G (Dense) + 2.5G (專家) + 2.56G (32K f16 KV Cache) = **7.71 GiB**，剛好滿載 3070 Ti 的 8GB 顯存而不發生溢出。

## 3. 多維度往復實驗報告

### 3.1 實驗一：上下文長度 (Context Size) 對 TPS 的免疫性
測試在 CPU MoE Baseline 混合推理模式下，上下文長度從 512 增加至 32K 時的解碼 TPS。
* **現象**：不論上下文長度為 512 還是 32K，解碼 TPS 均呈現一條近乎水平的線，起伏小於 1 TPS。
* **物理成因**：長上下文的 Self-Attention 複雜度高，但這部分運算被 100% 鎖定在 GPU (3070 Ti) 內以微秒級速度處理完畢。而 CPU 載入專家的數十毫秒級延遲依然主導了整個過程，因此上下文長度對 TPS 幾乎沒有副作用。

### 3.2 實驗二：MTP 投機窗口長度與甜蜜點演進
Qwen3.6 的 MTP 投機解碼並非使用獨立的「小草稿模型」，而是直接與主模型共享底層 Transformer 的特徵表示，在主模型最後一層的特徵輸出上並行預測後續 Token。
*   **物理成因與開銷特徵**：當投機驗證失敗時，主模型在該 step 並未進行重複計算（主模型始終只進行一次驗證 forward），其驗證失敗（Verification Fallback）的開銷主要來自 MTP Heads 多步預測的額外矩陣計算，以及草稿 KV cache 頁面的釋放與重新管理延遲。
*   **甜蜜點的硬體演進規律**：
    *   *純 CPU 推理（或單通道 Flex Mode）*：`n_max = 2` (投機 2 個 Token) 為黃金甜蜜點。拉大投機窗口至 3 或 4 會因為 CPU 計算 MTP Heads 額外矩陣與草稿頁面管理的開銷過大，導致速度暴跌至 17~19 TPS。
    *   *雙通道 64GB + GPU 專家卸載 (-ncmoe 35)*：由於 GPU 強大的矩陣與反量化運算算力，我們能夠以極低開銷抹平 MTP Heads 的預測與草稿管理延遲。此時 **`n_max = 3` (投機 3 個 Token) 成功演進為最新的「前台滿血最優甜點配置」**，將實測 Decode 速度最大化拉升至 **`35.02 TPS`**！

### 3.3 實驗三：Windows 前台排程紅利
* **現象**：當 llama-server 被放在獨立的前台新 CMD 視窗運行時，速度較背景 console 運行提速了 **20% (約 4 ~ 5.5 TPS)**。
* **物理成因**：Windows 作業系統賦予前台活動視窗 3 倍的 CPU 時間片分配與高精度定時器，大幅降低了多執行緒上下文切換的開銷。

## 4. 全自動網格調參最優配置總結
本專案開發了支援硬體自適應偵測的 `auto-tune-hyperparams.py` 調參腳本，尋優出的 RTX 3070 Ti 生產配置如下：

*   **Qwen3.6 Q4_K_M** 最佳生產指令：
    ```cmd
    start /high bin\llama-server.exe -m models\Qwen3.6-35B-A3B-MTP-Q4_K_M.gguf -np 1 -ngl 99 -ncmoe 35 --spec-type draft-mtp --spec-draft-n-max 3 --spec-draft-p-min 0.05 --numa none -c 32768 -fa on --cache-type-k f16 --cache-type-v f16 --no-mmap --mlock -b 4096 -ub 512 -t 6 -tb 8 --cpu-strict 0 --poll 50 --prio 3 --temp 0.6 --top-p 0.95 --jinja --host 127.0.0.1 --port 8888
    ```
*   **Qwen3.6 Q3_K_M** 最佳生產指令：
    ```cmd
    start /high bin\llama-server.exe -m models\Qwen3.6-35B-A3B-MTP-Q3_K_M.gguf -np 1 -ngl 99 -ncmoe 35 --spec-type draft-mtp --spec-draft-n-max 2 --spec-draft-p-min 0.12 --numa none -c 32768 -fa on --cache-type-k q8_0 --cache-type-v q8_0 --no-mmap --mlock -b 4096 -ub 512 -t 8 -tb 8 --cpu-strict 1 --poll 150 --prio 3 --temp 0.6 --top-p 0.95 --jinja --host 127.0.0.1 --port 8888
    ```

### 4.3 48K 極限長上下文的顯存預算與 WDDM Fallback 隱患
本專案雖然提供了 `start-qwen-35b-q4-48k-context.bat` 供使用者進行長文本極限測試，但在 Windows 環境下，該配置面臨極高的顯存溢出與效能雪崩風險：
*   **顯存二進位精確帳**：
    *   在 `-c 49152` (48K) 上下文下，僅 `q8_0` KV Cache 的顯存佔用就達到 **2.04 GiB**。
    *   加上 Dense 權重約 **2.80 GiB**，5 層 MoE 專家卸載約 **2.35 GiB**，以及 CUDA Runtime 獨佔的約 **0.40 GiB**。
    *   `llama-server.exe` 單一進程的獨佔顯存需求已達 **`7.59 GiB`**。
*   **WDDM Fallback 物理瓶頸**：
    *   Windows 桌面視窗管理員 (DWM) 與背景應用程式（如瀏覽器、Discord）會強制霸佔約 **0.60 ~ 1.20 GiB** 的 VRAM。
    *   這使得整機總顯存需求達到 **`8.19 ~ 8.79 GiB`**，絕對溢出了 RTX 3070 Ti 實體的 **`8.00 GiB`** 物理顯存限制！
    *   一旦溢出，Windows WDDM 驅動程式會強制將部分顯存分頁移至慢速系統 RAM（即 CUDA 系統內存）。這會導致 MoE 專家加載不得不通過慢速 PCIe 總線，造成推理速度發生斷崖式崩潰（由 35 TPS 暴跌至 14 TPS 左右）。
    *   **生產建議**：日常生產部署強烈建議固化於 32K 上下文（VRAM 佔用控制於 ~7.71 GiB 安全區內）。48K 上下文僅適合作為純 CPU 模式或背景應用程式完全清理乾淨時的「物理極限測試方案」。

## 5. 未來展望與 RTX 3080 20G 破局分析

如果將 GPU 升級為擁有 **20GB VRAM** 的 RTX 3080，由於 GQA（KV 頭數僅 2，頭維度 256）的物理特徵，200K 長上下文的 KV cache 僅佔用 **3.91 GB** (Q4_0) 或 **7.82 GB** (Q8_0)。

這將完全改寫推論規則：
1. **顯存分配**：3GB (Dense) + 7.82GB (200K Q8_0 KV Cache) = **10.82 GB**。
2. **專家載入空間**：剩下的 **9.18 GB** VRAM 可以用來將將近 50% ~ 70% 的 MoE 專家完全加載到 GPU VRAM 中。
3. **TPS 展望**：GPU 繞過慢速記憶體頻寬直接進行運算，即使在 **200K 超長上下文下**，推論速度亦可直衝 **`60 ~ 80+ TPS`**，徹底終結物理瓶頸！
