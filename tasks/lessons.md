# 本地 MoE 推理調優教訓與經驗總結 (lessons.md)

本文件記錄了在 NVIDIA RTX 3070 Ti (8GB VRAM) + 64GB RAM 的硬體邊界下，針對 35B MoE 模型（Qwen3.6 & Ornith-1.0）進行多維度尋優後獲得的核心教訓，以防後續重複犯錯。

---

## 🛑 核心教訓一：3-bit (Q3_K_M / IQ3_M) 量化在本地 MoE 混合推理下的效能陷阱

### 1. 現象與反直覺結果
在傳統思維中，模型檔案越小，記憶體搬運量越少，速度（TPS）應該越快。但在本專案實測中：
- **Ornith-1.0**：`IQ3_M` (22.29 TPS) 大幅落後於 `Q4_K_M` (27.43 TPS)，效能衰退達 **18.7%**。
- **Qwen3.6** (MTP 啟用)：`Q3_K_M` (29.09 TPS) 與 `Q4_K_M` (29.26 TPS) 幾乎持平，無速度優勢。

### 2. 根本原因剖析
- **反量化運算開銷 (De-quantization Overhead)**：
  3-bit 量化（特別是 imatrix 優化的 `IQ3_M`）其權重編碼格式極度複雜且零碎。CPU 在解碼（Decode）MoE 專家權重時，必須花費巨大的 SIMD 運算能力將其反量化為 FP16/FP32 浮點數。這項計算延遲已經**完全蓋過**了因為模型體積變小而節省的記憶體傳輸時間。
- **MTP 投機接受率（Acceptance Rate）的雪崩**：
  3-bit 精度損失大，使得 Qwen 的 MTP 草稿小模型預測準確度暴跌，草稿接受率從 Q4 的 **`~75%`** 跌落至 **`~50%`**。這導致頻繁觸發昂貴的**「回退重算開銷 (Verification Fallback)」**，主模型必須拋棄錯誤的草稿 Token 並重新計算，直接抵消了頻寬優勢。

### 3. 防止犯錯規則
- **規則一：** 在 CPU+GPU 混合推理模式下（使用 `ffn_exps=CPU` override 專家至系統記憶體時），**一律優先選用 Q4_K_M 格式**，不要盲目為了減少容量或追求 TPS 而切換至 3-bit。
- **規則二：** 面對 35B 以上 of MoE 模型，Q4 是本地部署的「速度與精度雙重國王」。3-bit 會導致「精度受損」且「速度變慢/持平」的雙重懲罰。

## 🛑 核心教訓二：Windows 進程前台排程紅利與背景退化限制

### 1. 現象與差異
在同一個控制台視窗背景執行 (`start /b`) 與獨立 cmd 新視窗前台執行 `llama-server.exe`，實測速度差異高達 **`20% ~ 23%`** (如 Qwen Q4 在單通道下背景 23.85 TPS vs 前台 29.26 TPS；在雙通道下背景 31.05 TPS vs 前台 35.02 TPS)。

### 2. 根本原因剖析
- **Windows 前台排程紅利 (Foreground Scheduling Bonus)**：
  Windows 作業系統預設會給予前台活動視窗 (Foreground Window) 及其關聯線程 **3 倍長的 CPU 時間片 (Time Slice)**，並賦予其高精度的系統定時器定時中斷頻率。
- **背景退化干擾**：
  若使用 `start /b` 將服務壓入 python 或其他腳本同一個 CMD 背景中運行，會被 Windows 判定為背景線程，不僅分配到的 CPU 時間片變短，還會因為與背景父行程共用控制台 I/O 而產生嚴重的排程上下文切換 (Context Switch) 開銷。

### 3. 防止犯錯規則
- **規則三：** 在 Windows 平台上測試或部署 `llama-server`，**一律禁止使用 start /b 或是將其壓在背景運行來進行效能評測**。
- **規則四：** 必須使用 `start` 啟動一個**獨立新 CMD 視窗前台運行**，以取得 Windows 作業系統滿血的前台排程與高精度定時器紅利！

## 🛑 核心教訓三：MTP 加速紅利被記憶體頻寬牆與反量化開銷抹平的現象

### 1. 現象與技術質疑
有 MTP 加速的 Qwen3.6 Q4 (29.26 TPS) 與無 MTP 的 Ornith-1.0 Q4 (27.43 TPS) 速度極度接近（僅差 1.83 TPS），未顯現出 MTP 理論上 1.2x ~ 1.4x 的加速幅度。

### 2. 根本原因剖析
- **Draft 運算與驗證回退代價**：
  MTP 每次投機預測都需要額外的 Draft Head 運算開銷。且雖然接受率高達 80%，剩餘 20% 預測失敗觸發的 Verification Fallback（回退重算）在 CPU 推理下成本極高，分流了部分加速效益。
- **KV Cache f16 解鎖反量化硬體優勢**：
  Ornith-1.0 由於無 MTP，KV Cache 被最佳化為 `f16` (零反量化開銷)；而 Qwen3.6 則必須維持 `q8_0` 以對齊草稿精度。`f16` 免除解壓計算所省下的時間，正好抵消並抹平了 Qwen 因 MTP 投機省下的頻寬時間。
- **單通道記憶體頻寬牆 (Memory Bandwidth Wall)**：
  在 $18.48 \text{ GB/s}$ 的極低頻寬下，讀取延遲主導了 90% 的時間，任何演算法優化都會被這面實體頻寬牆嚴重壓縮。

## 🛑 核心教訓四：KV Cache f16 在長上下文下的顯存溢出硬傷

### 1. 現象與容量制約
雖然 `f16` KV Cache 擁有免除 CPU 反量化的效能紅利，但其記憶體佔用是 `q8_0` 的 **`2 倍`**。
在 Ornith-1.0 的 32K (32768) 長上下文下：
- **`f16` 佔用容量**：高達 **`5.24 GB`**（加上 Dense 與系統背景共 11.74 GB，嚴重擠爆 VRAM，觸發 Slow PCIe Fallback 降速至 8 TPS）。
- **`q8_0` 佔用容量**：僅需 **`2.62 GB`**（總量約 8.62 GB，清理背景後可安全維持高速運行）。

### 2. 生產部署防錯規則
- **規則五：** **`f16` KV Cache 僅限用於短文本與極致 TPS 的展示場景**。
- **規則六：** 在長上下文（>8K）的生產環境中，**一律強制固化 `--cache-type-k q8_0 --cache-type-v q8_0`**，這是防範 8GB VRAM 顯存溢出導致速度雪崩的唯一物理防線。

## 🛑 核心教訓六：前端 HTML 資源動態調整與 JavaScript 語法健壯性防禦

### 1. 現象與連帶事故
在多次使用 Python 自動注入和還原網頁（如 Tab 分頁或效能卡片）的過程中，曾因字串替換範圍的邊界偏差，在 `initReportCharts` 函數中遺留了多餘的閉合括號 `}` 並破壞了大括號配對，導致全域 JavaScript SyntaxError。這造成瀏覽器完全拒絕執行該 script 區塊，進而使得完全無關的核心 Tab 按鈕全部點擊失效。

### 2. 根本原因剖析
- **動態注入的邊界污染**：使用 Python 腳本對複雜的 JavaScript 代碼做正則或子字串替換時，如果對大括號配對和代碼上下文界限不夠敏感，極易引入多餘或缺失括號。
- **全局運行時錯誤的波及效益**：JavaScript 屬單一線程，一旦在 `DOMContentLoaded` 事件或全域中拋出 `ReferenceError` 或 `SyntaxError`，會立即中斷後續所有代碼的初始化，致使前端功能大範圍崩潰。

### 3. 生產部署防錯規則
- **規則七**：對於任何前端 HTML/JS 的動態注入、修改或重構，**在宣佈修改完成前，必須將 JS 部分提取出來並使用 `node --check` 執行編譯期語法檢查**。
- **規則八**：在高風險邊界（如 Chart.js 圖表初始化、Tab 切換、網絡請求等）一律落實 **try...catch 的 Error Boundary 防禦**，並在最前端做 `typeof <Variable> === 'undefined'` 的安全防線，避免單點崩潰波及全域。

## 🛑 核心教訓七：Python 跨進程記憶體共享與 Windows 批次腳本語法陷阱

### 1. 跨進程數據返回格式的一致性
在 `multiprocessing` 中使用 `Manager().dict()` 進行跨進程通訊時，各工作進程返回的數據格式必須嚴格一致。在 `MemoryError` 異常分支返回單一 `float`，而正常分支返回 `tuple`，會導致主進程在使用 `r[0]` 遍歷結果時拋出不可訂閱錯誤（`TypeError`），引發整個測試的崩潰。所有分支必須一致返回 tuple（例如 `(0.0, 0.0)`）。

### 2. Windows 批次腳本迴圈變數轉義
在 Windows `.bat` 檔中，於 `FOR` 迴圈中定義與引用的變數必須使用雙百分號 `%%i`，而非互動命令列下的單百分號 `%i`。雖然未被引用的死碼變數不會直接引起 Crash，但會造成語法解析器警告並破壞腳本的語法完整性。

### 3. MTP 停用參數的邊界處理
在網格搜尋或優化腳本中，若要徹底停用投機解碼（MTP），必須在參數設計中顯式傳入 `0` 或做相應防禦。若僅傳入 `None` 且腳本退回模型默認值，會導致 MTP 始終處於開啟狀態（預設為 2），進而影響對比測試的真實性。

### 4. 防止犯錯規則
- **規則九**：所有跨進程的數據共享回傳，不論是正常還是異常分支，**都必須採用完全一致的資料結構**（如均為 Tuple 且長度相同）。
- **規則十**：在撰寫或生成 Windows 批次檔時，**所有的 `FOR /F` 迴圈變數一律使用雙百分號 `%%`**，且必須刪除或處理未使用的死碼變數以維持精簡。

## 🛑 核心教訓八：Windows cmd 命令行 start 指令的續行符號 (^) 陷阱

### 1. 現象與剖析
在 Windows 批次檔 (.bat) 中，`^` 被用作續行符號。但在 `start` 命令（如 `start /high "" "%LLAMA_SERVER%" ^`）中，使用 `^` 續行會被 cmd.exe 解譯為：
- `start` 的命令主體在第一行結束（這會在沒有任何參數的情況下啟動程序，或者以錯誤的空參數在新視窗運行）。
- 下一行的參數（如 `  -m "%MODEL_PATH%" ^`）會被 cmd.exe 視為**下一條獨立指令**在原視窗中直接執行，導致拋出 `'-m' is not recognized as an internal or external command` 錯誤並使腳本完全損毀。

### 2. 生產部署防錯規則
- **規則十一**：在 Windows 批次檔中透過 `start` 啟動任何外部程式時，**一律禁止使用 `^` 進行多行續行**，必須將指令與所有參數完整寫在同一行（扁平化單行命令），以防止 CMD 語法解譯器崩潰。

## 🛑 核心教訓九：Windows 環境下的 IPv6 localhost 連線阻斷與 Refused 陷阱

### 1. 現象與剖析
在 Windows 上，當伺服器（如 `llama-server`）綁定在 `0.0.0.0` 時，系統可能只會正確監聽 IPv4 的 `127.0.0.1` 埠口。此時如果 Python 客戶端（如 `requests`）使用 `localhost` 進行網路連線，Windows 系統可能會優先將 `localhost` 解析為 IPv6 的 `::1`。這會導致 Python client 直接回傳 `[WinError 10061] 無法連線，因為目標電腦拒絕連線。`
而在健康檢查等有多次重試或瀏覽器自身有 fallback 的環境下，可能會表現為偶發性連通，但後續的 completions 等大傳輸請求則會頻繁報錯。

### 2. 生產部署防錯規則
- **規則十二**：在編寫 Windows 下運行的測試或部署 Python 腳本時，**所有的 localhost 連線 URL 一律強制改寫為 `127.0.0.1`** 迴路 IP，直接繞過 Windows 的 IPv6 localhost 解析干擾，確保連線的絕對穩定。

## 🛑 核心教訓十：雙通道記憶體下的多執行緒與 SMT 競爭效能退化規律

### 1. 現象與剖析
在 64GB DDR4-3200 雙通道記憶體解鎖後（實測複製頻寬達 43.20 GB/s，唯讀頻寬達 33.46 GB/s，Peak Read 達 44.44 GB/s），原先的頻寬瓶頸已被部分解除。此時對 Qwen3.6 Q4 模型進行執行緒數壓測：
- **`-t 6`**（6 個執行緒）：跑出最優的 **`35.94 TPS`** 效能。
- **`-t 8` / `-t 12` / `-t 16`**：效能反而降為 **`~29 TPS`**。
原因在於，Ryzen 7 5700X 為 8核16執行緒（8C/16T）。當執行緒設為 8 以上時，操作系統容易將推理計算分配至同一個實體核心的超執行緒（SMT）上進行競爭，或者因為執行緒數過多引發額外的上下文切換與快取失效開銷，導致 TPS 顯著衰退。

### 2. 生產部署防錯規則
- **規則十三**：在 Ryzen 8 核心 CPU 上進行 MoE 混合推理時，即使在雙通道高頻寬下，**解碼執行緒數 `-t` 仍應強制固化為 `6`**。多於 6 執行緒會觸發 SMT 超執行緒爭用，導致效能反而退化至背景瓶頸值。

## 🛑 核心教訓十一：自動測試測速腳本中的 Warmup 缺失與 Prompt 特徵對 MTP 接受率的干擾

### 1. 現象與剖析
雖然雙通道解碼極限高達 35.94 TPS，但在 `validate-inference-tps.py (已清理過時歷史腳本)` 測速時卻只跑出了 29.68 TPS。這有兩個深層原因：
- **缺乏 Warmup**：測速腳本直接統計首個請求的生成速度，使得首字延遲（TTFT，包含 prefill 時間）和 PyTorch/requests 建立連接的延遲被平均分配到了解碼 TPS 中，拉低了數值。
- **MTP 接受率特徵干擾**：MTP 對於繁體中文或流暢對話有極高的草稿接受率（>75%），但當 Prompt 產出含有大量英文程式碼、結構化標記或長思維鏈（如思考區塊）時，MTP 草稿模型猜測的準確度會降至 50% 以下，觸發 Verification Fallback 重算，使得雙通道優勢被 CPU 重算開銷抹平。

### 2. 生產部署防錯規則
- **規則十四**：任何基準測試（Benchmark）或測速腳本在正式統計 TPS 前，**必須至少進行一次 Warmup 推理**以排除首字與載入干擾，並且應統一使用簡短中文字句作為測速 Prompt，以真實反映雙通道 + MTP 的極限解碼效能。

## 🛑 核心教訓十二：Windows 批次檔 nested parenthesis (巢狀括號) 語法崩潰與管道符號地雷

### 1. 現象與剖析
在重構批次檔引入 Web UI 載入探測時，點選選單選項後 cmd 視窗直接「閃退無回應」。此錯誤源自於 Windows CMD 解析引擎的底層硬傷：
- **括號內 label 致命 Bug**：在 `if (...)` 或 `for ... do (...)` 的括號內，定義標籤（例如 `:server_ready`）為 CMD 語法大忌。parser 在預編譯括號樹時會發生結構性錯亂，直接引發 cmd.exe 進程崩潰閃退。
- **括號內管道符號 `|` 解析崩潰**：在 nested parenthetical blocks（多層括號嵌套）內部直接寫入 `curl ... | findstr ...` 管道，若未轉義，CMD 會提前截斷 `FOR` 迴圈並判定括號不匹配，拋出 `... was unexpected at this time.` 解析錯誤。

### 2. 生產部署防錯規則
- **規則十五**：Windows 批次檔在進行複雜條件等待或 loop 邏輯時，**一律嚴禁在 `IF/FOR` 的 `()` 括號內部定義 label 或使用複雜的管道符號 `|`**。應統一採用「括號內僅 goto 跳轉、括號外定義 label」的扁平結構；且對於 Web 探測，一律使用 `curl -s -f <URL> >nul 2>&1`，免除 `findstr` 與 `|` 管道，以確保 Windows CMD 引擎 100% 健壯。

## 🛑 核心教訓十三：Windows 多語系 CMD 在 UTF-8 下的亂碼解析閃退天坑與「純 ASCII/英文」防錯金科玉律

### 1. 現象與剖析
在將批次檔重構為 unnested 結構後，使用者在點擊 `start.bat` 時依然遇到「點開輸入選項閃退就沒東西了」。此天坑源於 CMD 在多語系環境下的解析致命缺陷：
- **字碼頁切換障礙與亂碼誤判**：若使用者的 Windows CMD 預設為 `cp950`（Big5），當其讀取以 UTF-8 儲存的批次檔時，所有中文（例如 `正在等待`）都會被還原成無意義的亂碼。
- **亂碼觸發控制字元地雷**：這些亂碼的二進位編碼中，極易隨機出現 `0x7C` (`|`)、`0x29` (`)`)、`0x28` (`(`) 等 CMD 特殊控制字元。CMD parser 會誤將這些亂碼當成語法結構，進而破壞括號配對或執行錯誤管道，導致指令解析崩潰並瞬間閃退。

### 2. 生產部署防錯規則
- **規則十六**：所有在 Windows 下由用戶直接雙擊或互動式執行的 `.bat` 批次檔，**一律嚴禁包含任何中文字元或多位元組字元，必須 100% 保持純 ASCII/英文**。任何 Log、橫幅、進度提示、錯誤警告，必須全部以英文呈現，從根源杜絕 Windows 多語系 CMD 的解碼閃退崩潰。

## 🛑 核心教訓十四：Windows Excluded Port Range (連接埠排除範圍) 導致 Socket 綁定拒絕與新視窗閃退

### 1. 現象與剖析
在修復了控制台與腳本的 CMD 解碼與語法錯誤後，使用者在輸入數字啟動模型時，新彈出的推理伺服器終端視窗「只閃一下就消失了（閃退）」。經當前終端無 `start` 裸跑 `llama-server.exe` 診斷，拋出 `couldn't bind HTTP server socket` 錯誤。此網路層天坑原因為：
- **Windows NAT (WinNAT) 隨機鎖死埠區**：當系統啟用 Hyper-V、Docker 或進行 Windows Update 重啟後，WinNAT 服務會隨機保留並排除（Exclude）數千個 TCP 連接埠範圍（Exclusion Ranges）。
- **埠衝突 Permission Denied**：若 `llama-server` 預設的 `8080` / `8088` 埠不幸落入這些隨機排除區間，Windows 會拒絕任何普通進程 bind 該埠（WSAEACCES），導致伺服器崩潰退出。由於這是系統重啟後隨機決定的排除區，這完全解釋了為何「之前能用，今天卻突然壞了」。

### 2. 生產部署防錯規則
- **規則十七**：所有本機 API 服務埠一律禁止使用極易落入 WinNAT 排除區或與開發衝突的 `8080`、`8088` 等預設埠。一律強制遷移至安全不被排除的 **`8888`**（或非 Exclusion Range 埠），並同時將伺服器綁定主機名固定為 `--host 127.0.0.1` 以避免 IPv4/IPv6 雙棧 Socket 衝突。

## 🛑 核心教訓十五：Qwen MoE GQA (Grouped Query Attention) 結構真相與 KV Cache 記憶體開銷
### 1. 現象與剖析
在評估 Qwen-35B-A3B 長上下文時，原先盲目採用傳統 MHA 估算公式，導致 200K 上下文的 KV Cache 用量被高估了 8 倍。經直接從 GGUF 的元數據（Metadata）讀取證實：
- **GQA 特徵**：Qwen-35B-A3B 採用的是 `head_count_kv = 2` 的 Grouped Query Attention 結構，而不是 MHA。這導致每個 Token 的 KV Cache 記憶體消耗大幅度縮減。
- **41 層設計**：層數並非整數的 40 層，而是實體載入 41 層，這使 elements/token 細微增多。
- **量化與 FP16 開銷**：在 GQA 下，200K context 對於 `FP16` 僅需 **15.64 GiB**，`Q8_0` 僅需 **7.82 GiB**，而 `Q4_0` 僅需 **3.91 GiB**。
- **自動調參的 f16 KV 快取紅利**：調參壓測證實，在短/中上下文（<32K）下，由於 VRAM 極度充裕，設定 `--cache-type f16` 能夠省去解壓與反量化的計算開銷，直接提供額外的 TPS 增長，使 Q4 達到 **35.02 TPS** 的歷史峰值。

### 2. 生產部署防錯規則
- **規則十八**：估算任何 LLM（特別是 MoE 模型）的 KV Cache 用量前，**必須直接從 GGUF 模型元數據中查明其真實 KV 頭數 (head_count_kv) 與層數 (block_count)**，嚴禁憑主觀經驗臆斷。
- **規則十九**：在 VRAM 充足且上下文較短（如 32K 內）的推論部署中，**優先使用 `--cache-type f16` 作為 KV 快取格式**，以最大化推論 TPS；而對於記憶體/顯存吃緊或超長上下文（如 48K+）的部署，則應強制回退至 `q8_0` 以防觸發 WDDM Fallback。

## 🛑 核心教訓十六：開源專案的大檔案 Git 排除與環境變因透明化
### 1. 現象與剖析
在準備將部署專案開源至 GitHub 時，必須嚴格控管代碼庫體積與敏感度：
- **GGUF 大檔案地雷**：若將數十 GB 的 `*.gguf` 權重檔案直接提交，會導致 Git 存儲庫直接撐爆。
- **可執行二進位檔排除**：`bin/` 資料夾下的 `llama-server.exe` 與 DLL 檔案在不同 Windows/Linux、CUDA/CPU 環境下編譯版本不同，強行打包會導致相容性地雷，應予以 gitignore，並提供清晰的下載指引。
- **環境實驗變因透明化**：本機推理速度（TPS）極度取決於硬體（特別是記憶體頻寬）。若不向使用者寫明「硬體規格（CPU, GPU, RAM 通道）」與「實測單雙通道頻寬差距（33.46 GB/s vs 18.48 GB/s）」，使用者下載執行後會因 TPS 的落差而感到困惑。

### 2. 生產部署防錯規則
- **規則二十**：任何將要開源部署的代碼庫，**必須預先配置完好的 `.gitignore`**，嚴格排除 `*.gguf`、`bin/` 底下平台相關可執行檔及本地 `*.log` 日誌檔案。
- **規則二十一**：在 `README.md` 說明書的顯眼處，**必須寫明開發者的硬體測試環境與記憶體單/雙通道頻寬實測值**，並將說明引導至綜合分析報告中，保證知識傳遞的完整度與可復現性。

## 🛑 核心教訓十七：新版 llama.cpp 廢除 `--numa none` 引發啟動視窗閃退天坑

### 1. 現象與剖析
在本專案更新最新官方 `llama.cpp` 引擎後，雙擊模型啟動腳本時，新彈出的 high-priority CMD 視窗會一瞬間自我消失並閃退。
經在當前終端手動拉起服務捕獲錯誤發現，原因為 `error while handling argument "--numa": invalid value`。最新版 `llama.cpp` 重新編排了 NUMA 參數解析，**廢除了舊版接受的 `none` 值**。在新版中，傳入 `--numa none` 會被視為 invalid 錯誤並以退出碼 1 崩潰。如果不需要 NUMA 優化，正確做法是**在命令行中完全不傳遞 `--numa` 參數**。

### 2. 生產部署防錯規則
- **規則二十二**：在任何部署與啟動腳本中，**嚴禁硬編碼 `--numa none` 參數**。NUMA 參數必須在生成器（如 `rebuild-bat-files.py`）中進行動態判定，僅在 `numa` 數值不為 `"none"` 時才在命令列追加 `--numa`，否則完全忽略該參數，以防二進位版本升級後導致啟動視窗閃退。
