Section 01

🏗️ 模型架構深度解析

理解 Qwen3.6-35B-A3B 的 Hybrid MoE 架構，是所有優化策略的基礎。

📐 Hybrid 混合注意力架構

模型由 10 個循環組成，每循環包含 3 層 Gated DeltaNet（線性注意力）+ 1 層 Gated Attention（標準 GQA），共 40 層。

Gated DeltaNet（30 層）— 線性注意力，固定 State
Gated Attention（10 層）— GQA，產生 KV Cache
🎯 關鍵洞見：只有 10/40 層會產生 KV Cache！DeltaNet 使用固定大小的 recurrent state（~60 MiB），不隨 context 長度增長。這讓 262K context 在 8GB VRAM 上成為可能。

💡 MoE 卸載的精妙之處：傳統的全局層卸載需要在 PCIe 上搬運大量權重矩陣。而 --cpu-moe 的核心思路是：只傳輸極小的 Activation Vector（~4-16 KB/token/layer），由 CPU 在 RAM 中直接完成 Expert FFN 矩陣乘法，再將結果送回 GPU。PCIe 頻寬完全不是瓶頸。

⚙️ llama.cpp 參數全攻略

每一個參數都經過精心計算，確保在 8GB VRAM 上榨乾每一滴效能。

🎮 GPU / CPU 層卸載

▼
參數設定值說明
-ngl 99 99（最大化） 將所有可放入 VRAM 的層全部載入 GPU。llama.cpp 會自動適配實際可用空間。
--cpu-moe 啟用 將所有 MoE Expert 權重路由至 CPU RAM。這是 8GB VRAM 的核心策略。
--n-cpu-moe N 備選 與 --cpu-moe 二選一。可精細控制卸載層數（如 35 = 前 35 層的 Expert 放 CPU）。
原理：使用 --cpu-moe 後，GPU 只保留 Dense 層（Attention + Norms），Expert FFN 全部在 CPU 計算。推理時只有極小的 Activation Vector 跨 PCIe 傳輸。

🔥 熱門 Expert 快取

▼
參數設定值說明
--moe-expert-cache-size N 4 ~ 8 在 VRAM 中快取 N 個最常被路由的 Expert。利用齊夫定律（Zipf's Law），~20% 的 Expert 處理 ~80% 的 Token。
效能加速原理：每個 Expert 在 Q4_K_M 下僅 ~0.5-2 MB。快取 8 個 Expert 只額外佔用 ~4-16 MB VRAM，但能將 PCIe 通訊減少 ~80%，極高 ROI。

🗂️ KV Cache 量化

▼
參數設定值說明
--cache-type-k q8_0 q8_0 KV Cache Key 量化為 Q8_0。品質幾乎無損，記憶體減半。
--cache-type-v q8_0 q8_0 KV Cache Value 量化為 Q8_0。
進階選項：若需要極長 context（262K），可改用 q4_0 或 q4_1，KV Cache 再縮小一半。但可能影響長文本注意力品質。
注意：使用量化 KV Cache 必須在編譯 llama.cpp 時開啟 -DGGML_CUDA_FA_ALL_QUANTS=ON。

⚡ Flash Attention

▼
參數設定值說明
--flash-attn / -fa 啟用 必須啟用。大幅降低 Attention 計算的記憶體使用，並加速 KV Cache 量化在 GPU 上的執行。

🚀 原生 MTP 多 Token 預測

▼
參數設定值說明
--spec-type draft-mtp 啟用 使用模型內建的 MTP 預測頭進行投機解碼。零額外 VRAM 負擔。
--spec-draft-n-max 2 每次前向傳播預測最多 2 個候選 Token。甜蜜點，接受率 >80%。
--spec-draft-p-min 0.5 候選 Token 信賴度門檻。低於此機率的預測會被丟棄，避免浪費計算。
⚡ 速度提升 ~1.4-2.2x！需使用 MTP 版本的 GGUF 檔案（如 unsloth/Qwen3.6-35B-A3B-MTP-GGUF）。標準 GGUF 不包含 MTP 預測頭，此參數無效。

🧊 記憶體管理

▼
參數設定值說明
--no-mmap 啟用 Windows 上建議使用。禁用 mmap，直接將模型載入 RAM，避免分頁延遲。
--mlock 啟用 鎖定記憶體頁面，防止 OS 將模型權重換出至 pagefile。

📋 前置需求

  • Visual Studio 2022（安裝「使用 C++ 的桌面開發」工作負載）

  • 最新 NVIDIA 顯卡驅動
📂 編譯指令（Developer Command Prompt for VS 2022）
:: 1. Clone llama.cpp
git clone https://github.com/ggerganov/llama.cpp
cd llama.cpp

:: 2. 建立 build 目錄並設定 CMake
mkdir build
cd build

:: 3. 關鍵編譯旗標：
::    -DGGML_CUDA=ON          → 啟用 CUDA GPU 加速
::    -DGGML_CUDA_FA=ON       → 啟用 Flash Attention
::    -DGGML_CUDA_FA_ALL_QUANTS=ON → 支援所有量化 KV Cache 類型
::    -DCMAKE_CUDA_ARCHITECTURES=86 → RTX 3070 Ti (SM 8.6)
cmake .. ^
  -DGGML_CUDA=ON ^
  -DGGML_CUDA_FA=ON ^
  -DGGML_CUDA_FA_ALL_QUANTS=ON ^
  -DCMAKE_CUDA_ARCHITECTURES=86 ^
  -DCMAKE_BUILD_TYPE=Release

:: 4. 編譯（-j 8 使用 8 線程平行編譯）
cmake --build . --config Release -j 8

:: 5. 完成後執行檔位於：build\bin\Release\
::    llama-server.exe, llama-cli.exe 等
🚨 重要：若不加 -DGGML_CUDA_FA_ALL_QUANTS=ON，量化 KV Cache（如 q8_0, q4_0）的計算會被強制回退到 CPU，導致推理速度嚴重退化！

🧠 核心洞見

為什麼這個「不可能的任務」其實是可行的。

💡 洞見 1：MoE = 偽裝的 3B 模型

雖然總參數 35B，但每個 Token 只啟用 3B。計算量等同於 3B dense 模型，但擁有 35B 的知識容量。GPU 只需要處理 3B 的計算強度。

💡 洞見 2：Hybrid 架構的 KV Cache 奇蹟

30/40 層使用 DeltaNet（固定 60 MiB state），只有 10 層需要 KV Cache。262K context 的 KV Cache 僅 2.56 GB（FP16），比傳統架構少 4 倍。

💡 洞見 3：72 GB RAM 是秘密武器

Q4_K_M 模型僅 ~21 GB，RAM 使用率不到 30%。即使換用 Q8_0（~38 GB），仍有 34 GB 餘裕。RAM 完全不是瓶頸。

💡 洞見 4：PCIe 4.0 x16 完全夠用

--cpu-moe 只傳輸 Activation Vector（~4-16 KB/token/layer），不搬運完整 Expert 權重。25 GB/s 的 PCIe 頻寬在此場景下完全不是瓶頸。

📊 1. 記憶體物理頻寬與 Flex Mode 退化診斷
🔍 Flex Mode 混插非對稱單通道退化

本機採用 8GB + 16GB + 16GB + 32GB 混插的大雜燴記憶體。不同容量、廠牌混插導致主機板定址退化為 Flex Mode 非對稱單通道運作，且記憶體控制器為了相容性放寬了記憶體時序（Latency 延遲），造成隨機跳轉定址時發生大量的 匯流排空轉 (Bus Bubbles)。

🚀 2. 突破頻寬鐵壁的加速三板斧
1️⃣ MTP 投機解碼 (預測窗口限制為 2)

經全自動參數網格調優，將投機預測窗口限制為 `2` 個 Token (而非預設的 4 個)。在 83%~88% 的高接受率下，此配置可極大降低預測錯誤後的驗證開銷，相較於 4 個窗口速度提升了 16%，成功實現 2.28x 的投機加速比！

2️⃣ 物理核心綁定 (--cpu-strict 1)

設定 -t 8 -tb 8 飽和 Ryzen 5700X 的 8 個實體核心，避免超執行緒 (SMT) 的頻寬競爭。開啟 --cpu-strict 1 強制核心綁定，禁止 Windows 調度器將執行緒跨核漂移，最大化處理器的 L1/L2 快取命中率。

3️⃣ 自旋鎖退避 (--poll 0)

將自旋鎖設為 0。自旋鎖為 0 可讓空閒核心在無工作時及時退讓，防止 CPU 因持續高負載發熱降頻，並優化 GPU/CPU 同步調度，為推論速度帶來額外 2 TPS 收益。

🔒 3. KV Cache 顯存管理與防 WDDM Fallback 機制
⚠️ WDDM VRAM Fallback 降速陷阱

當 context 設定為 32768 時，llama-server 預設會為 4 個 Slot 併發分配 KV Cache (n_parallel = 4)，導致其顯存佔用高達 10.48 GB。加上骨幹 Dense 權重的 3 GB，總計高達 13.48 GB，嚴重溢出 RTX 3070 Ti 的 8GB VRAM。

這會觸發 Windows 的 WDDM Fallback 機制，自動將分頁轉移至系統記憶體，迫使 GPU 經由慢速 PCIe 進行讀取，TPS 直接被腰凍至 14.29 TPS。

Fallback (14.29 TPS) 鎖定 NP=1 (28.09 TPS)
🛡️ 槽數限制與 KV Cache 量化甜蜜點

為了榨乾 8GB VRAM 同時防止 Fallback，我們實施了以下兩大核心防禦措施：

• 限制併發槽數 (-np 1)：將 Slot 數強制鎖定為 1，使 KV cache 顯存佔用降至 2.62 GB，總顯存需求僅 5.62 GB，完美安全塞入 8GB VRAM 中，性能重回 28+ TPS。
• KV Cache 8-bit 量化 (q8_0)：KV cache 是動態 Activation，對精度極度敏感。使用 8-bit 可以節省 50% 顯存且幾乎無損精度，而 4-bit KV Cache (q4_0) 會造成長上下文 PPL 困惑度呈指數級上升（邏輯崩潰與幻覺），且因為反量化開銷在很多硬體上反而變慢。

🌌 極限長上下文擴展 (48K Context)

為了把非模型佔用的空間通通留給模型，以擴展最大上下文，我們編寫了 free-background-vram.bat 強制結束桌布引擎、Discord 等背景吃顯存的程式，安全回收 2 - 3 GB VRAM。

在 8-bit KV Cache 且 -np 1 的設定下，48K (49152) 上下文需約 3.93 GB KV Cache，加上骨幹 Dense 的 3 GB，總需求為 6.93 GB。背景清理乾淨後，可完美塞進 8GB 實體顯存，實現無損長上下文的滿血高速推理！

⚡ Q4 量化模型極限衝刺與前台排程紅利 (OS Scheduling vs. TPS)
前台排程加速
實測揭示，當 llama-server.exe 在 Windows 獨立前台視窗運行時，速度大幅衝上 27 ~ 29 TPS；而被壓入背景（與 Python 腳本共用控制台背景）時則限制在 22 ~ 23 TPS！
原理解析：Windows 會給予前台活動視窗及其執行緒高達 3 倍的 CPU 時間片與高精度定時器，大幅降低了 MoE 專家解碼時的線程上下文切換開銷，釋放了額外 20% 的硬體隱形算力。此外，在短文本下將 KV Cache 設定為 f16 能徹底免除反量化計算開銷，成為衝刺 70+ TPS 雙通道時代的黃金配置。

🧱 基礎概念 8 個術語
LLM 大型語言模型
基礎
Large Language Model 的縮寫。一種經過海量文本資料訓練的 AI 模型，能理解和生成人類語言。ChatGPT、Claude、Qwen 都是 LLM。
就像一個讀了全世界圖書館所有書的超級學霸，你問什麼問題它都能給出答案。Qwen3.6-35B-A3B 就是這樣一個「學霸」。
Parameter / Weight 參數 / 權重
基礎
模型在訓練過程中學到的「知識」，以數字形式儲存。每個 parameter 就是一個浮點數。35B = 350 億個參數，代表模型內部有 350 億個數字在協同運作。模型的參數越多，理論上越聰明，但也越佔空間。
如果把大腦比喻成模型，那「參數」就像是大腦裡的「突觸連結」。突觸越多，腦子越聰明，但也越耗能量。一個 35B 的模型就像有 350 億個突觸的超級大腦。
Token 令牌 / 詞元
基礎
模型處理文字的最小單位。不是一個字，也不是一個詞，而是模型自己切分出來的片段。英文大約 1 個單詞 ≈ 1.3 token，中文大約 1 個字 ≈ 1.5–2 token。
想像你在拼樂高。「Token」就是每一塊樂高積木。模型不是一次讀整句話，而是把句子拆成一塊塊積木來處理。「你好世界」可能會被拆成「你」「好」「世界」三個 token。
Inference 推理
基礎
模型「思考並回答問題」的過程。當你輸入一段文字，模型根據其內部的參數計算出回覆——這個計算過程就叫推理。和「訓練」（模型學習知識）是相對的概念。我們部署模型的目的就是做推理。
「訓練」= 學生讀書學習；「推理」= 學生坐在考場上答題。我們現在做的就是讓這個學霸坐到你的電腦上答題。
Context Window / Context Length 上下文視窗 / 上下文長度
基礎
模型一次對話中能「記住」的最大文字量，以 token 為單位。262K = 262,144 tokens，大約等於一整本小說。context 越長，模型能參考的資訊越多，但也越消耗記憶體。
就像你的工作桌面大小。桌面越大，你能同時攤開越多文件參考。262K context 就像一張超大辦公桌，可以同時攤開一整本書來翻閱。但桌子越大，需要的房間（記憶體）也越大。
Tensor 張量
基礎
存放數據的多維數組（可以理解為高維度的表格）。模型的所有參數都以 tensor 的形式存放。一維 tensor = 向量（一列數字），二維 tensor = 矩陣（一張表格），三維以上就叫「張量」。
一維張量像一條項鍊（一串珠子），二維張量像一張 Excel 表格（行×列），三維張量像一疊表格（行×列×頁）。模型的權重就是一堆這樣的高維度表格。
Layer 層
基礎
模型的基本組成單元。模型像三明治一樣一層一層堆疊。輸入的文字從第 0 層進去，每經過一層就被「理解」得更深一點，最後從第 39 層輸出答案。Qwen3.6-35B-A3B 有 40 層。
像工廠的流水線。原料（你的文字）從第一道工序進去，經過 40 道工序加工，每一道工序都讓產品更精緻，最後出來的就是模型的回答。
Forward Pass 前向傳播
基礎
資料從模型的輸入端（第 0 層），逐層通過每一層的計算，最終到達輸出端產生結果——這整個過程叫做一次「前向傳播」。模型每生成一個 token，都要做一次完整的前向傳播。
就像一顆彈珠從柏青哥機器頂部丟下去，一路撞過各種釘子（每一層的計算），最後掉進底部的某個洞（輸出某個 token）。
🏗️ 模型架構 7 個術語
Transformer 變換器架構
架構
幾乎所有現代 LLM 的骨架。2017 年由 Google 提出，核心是「自注意力機制」——讓模型在處理每個字時，能同時「看到」句子中的所有其他字，判斷哪些字跟當前的字最有關係。
傳統模型像從左到右逐字閱讀的人，看到第 100 個字時已經忘了第 1 個字。Transformer 則像能同時看到整頁所有文字的人，可以瞬間判斷哪些字之間有關聯。
Hidden Size 隱藏維度
架構
模型內部用多少個數字來「描述」一個 token。Qwen3.6-35B-A3B 的 hidden size 是 2048，代表模型把每個 token 理解成一個包含 2048 個數字的向量。越大代表模型能捕捉越豐富的語意特徵。
如果用文字描述一個人，你可以只說「高」「矮」（2 維），也可以描述身高、體重、膚色、髮型……等 2048 個維度。維度越多，描述越精確。
Embedding 嵌入層
架構
模型的「翻譯入口」。把人類的文字 token 轉成模型能理解的數字向量。Qwen3.6 有 248,320 個詞彙，每個詞彙對應一個 2048 維的向量。這個對照表就叫 Embedding 層。
就像字典。你查「蘋果」，字典會給你一段定義。Embedding 層就是模型的字典——查「蘋果」這個 token，它會給出一組代表「蘋果」含義的 2048 個數字。
FFN (Feed-Forward Network) 前饋神經網路
架構
模型每一層裡面的「知識存儲區」。由簡單的矩陣乘法和激活函數組成。注意力機制負責「理解關係」，FFN 負責「運用知識」。在 MoE 模型中，FFN 部分被拆分成很多個 Expert（專家），這就是模型參數佔大頭的地方。
注意力機制 = 讀題（理解問題問什麼），FFN = 答題（運用知識給出答案）。MoE 的做法是把「答題」這步拆給 256 個專科老師，每次挑最懂的 8 個來回答。
Vocabulary Size 詞彙表大小
架構
模型認識多少個「詞」。Qwen3.6-35B-A3B 的詞彙表有 248,320 個 token。包含中文字、英文單詞片段、標點符號、程式碼片段等。模型只能理解和輸出詞彙表內的 token。
Hybrid Architecture 混合架構
架構
Qwen3.6-35B-A3B 同時使用兩種不同的注意力機制：Gated DeltaNet（線性注意力，30 層）和 Gated Attention（標準注意力，10 層），交替堆疊。這是它最大的架構特色。好處是只有 10 層需要 KV Cache，大幅減少記憶體消耗。
就像一棟 40 層的大樓，30 層是普通辦公室（DeltaNet，不需要額外儲物間），10 層是有大型檔案室的特殊樓層（Gated Attention，需要 KV Cache）。所以整棟大樓的儲物空間需求只有純檔案室大樓的 1/4。
YaRN Yet Another RoPE Extension
架構
一種讓模型處理比訓練時更長的上下文的技術。Qwen3.6-35B-A3B 原生支援 262K tokens，但透過 YaRN 可以延伸到約 1,010,000 tokens（超過 100 萬！）。原理是動態調整位置編碼的頻率。
⚡ MoE 專家系統 7 個術語
MoE (Mixture of Experts) 混合專家模型
核心
這是整個部署計畫的核心概念！傳統模型（Dense Model）每一個 token 都要經過所有參數計算。MoE 模型則把 FFN 部分拆成很多個「Expert（專家）」，每個 token 只挑選少數幾個 Expert 來處理。

Qwen3.6-35B-A3B：256 個 Expert，每次只啟用 8+1 個。所以雖然有 35B 參數，每個 token 只用到 ~3B。

就像一家大醫院有 256 個專科醫生。你來看病時，掛號台（Router）只會幫你安排 8 個最對口的醫生會診，而不是讓 256 個醫生都來看你。這樣醫院的容量可以很大（35B 參數），但每次看診的成本很低（只用 3B）。
Expert 專家
MoE
MoE 模型中的基本計算單元。每個 Expert 就是一個獨立的小型 FFN 網路，包含 Up、Down、Gate 三個矩陣。它們各自「專精」於處理不同類型的知識。在 Qwen3.6-35B-A3B 中，每個 Expert 的中間維度是 512。
就像醫院裡的專科醫生。心臟科醫生擅長心臟問題，骨科醫生擅長骨頭問題。模型裡的 Expert 也是如此，有的擅長處理程式碼，有的擅長處理數學，有的擅長處理中文。
Router / Routing 路由器 / 路由
MoE
MoE 模型中負責「選專家」的機制。每當一個 token 到達 MoE 層時，Router 會根據 token 的特徵，從 256 個 Expert 中選出最適合的 8 個來處理這個 token。Router 本身是一個很小的神經網路。
醫院的掛號台/分診台。病人（token）進來後，分診台（Router）判斷你的症狀，把你分配給最對口的醫生（Expert）。
Shared Expert 共享專家
MoE
一個每次都會被啟用的特殊 Expert。不管 Router 選了哪 8 個 Expert，Shared Expert 都會參與計算。它負責處理所有 token 都需要的「通用知識」（如基本語法），所以每次實際啟用的是 8 路由 + 1 共享 = 9 個 Expert。
就像醫院裡的全科醫師（家庭醫學科），不管你什麼病都會先經過他。然後再配上 8 個專科醫師做會診。
Active Parameters 每 Token 啟用參數
MoE
MoE 模型中，每個 token 實際「用到」的參數量。Qwen3.6-35B-A3B 的 Active Parameters 是 ~3B。這代表它的計算速度等同於一個 3B 的小模型，但品質接近 35B，因為所有 256 個 Expert 的知識都可以被調用。
一本百科全書有 35 冊（35B 參數），但你查一個問題只需要翻 3 冊（3B 活躍參數）。查閱速度很快，但背後有完整的百科知識庫在支撐你的答案品質。
Dense Model / Dense Layer 稠密模型 / 稠密層
MoE
Dense（稠密）= 每個 token 都經過所有參數計算，沒有「跳過」任何部分。和 MoE（Sparse，稀疏）相對。
在 Qwen3.6-35B-A3B 中，Attention 層是「Dense」的（每次都全部執行），而 FFN 層是「Sparse/MoE」的（只用 9/256 個 Expert）。
部署計畫中說的「Dense 層放 GPU，Expert 放 CPU」就是指：把每次都要用的 Attention 放在快速的 GPU 上，不常用的 Expert 放在大容量的 RAM 裡。
Zipf's Law 齊夫定律
MoE
一個統計規律：少數 Expert 被使用的頻率遠高於其他 Expert。大約 15–20% 的「熱門 Expert」處理了 80% 的 token。這個特性讓「Expert 快取」策略成為可能——只要把最常用的幾個 Expert 放在 GPU 快取中，就能避免大部分的 CPU↔GPU 資料傳輸。
就像你手機裡裝了 200 個 App，但 80% 的時間你只用 LINE、YouTube、Chrome 這幾個。所以把這些常用 App 放在手機桌面（GPU 快取），其他的放在 App 資料夾裡（CPU RAM）就好。
🧠 注意力機制 8 個術語
Self-Attention 自注意力機制
注意力
Transformer 的核心。讓模型在處理每個 token 時，計算它和所有其他 token 之間的「相關程度」。比如在「貓追老鼠」這句話中，「追」和「貓」的關聯度高（因為貓是主詞）。

具體來說，每個 token 會被轉換成三個向量：Q（Query，問題）、K（Key，鑰匙）、V（Value，答案）。Q 和所有的 K 做比對，得到「注意力分數」，再用這個分數加權取 V 的結果。
Token "追" 的處理過程： Q("追") × K("貓") = 0.8 ← 高度相關！ Q("追") × K("老鼠") = 0.7 ← 相關 Q("追") × K("。") = 0.1 ← 不太相關 最終 "追" 的理解 = 0.8×V("貓") + 0.7×V("老鼠") + 0.1×V("。")
KV Cache 鍵值快取
核心
部署計畫中最重要的記憶體消耗者之一。模型在生成回覆時，每生成一個新 token 都需要參考之前所有 token 的 K 和 V 向量。如果每次都重新計算，效率太低。所以把之前算好的 K 和 V 存起來，這就是 KV Cache。

KV Cache 會隨著 context 長度線性增長。context 越長，需要存的 K 和 V 就越多。Qwen3.6-35B-A3B 的優勢是只有 10 層需要 KV Cache（Gated Attention 層），其他 30 層用的是固定大小的 DeltaNet State。
你在寫一篇很長的文章。每寫一個新句子，你都需要回頭看之前寫了什麼（確保前後連貫）。KV Cache 就像你的草稿紙——把之前寫過的重點摘錄下來，這樣不用每次都從頭讀整篇文章。文章越長，草稿紙就越厚。
Attention Head 注意力頭
注意力
注意力機制被拆分成多個平行的「頭」，每個頭獨立計算注意力，然後合併結果。不同的頭可以學到不同種類的關係：有的學語法，有的學語義，有的學位置關係。

Qwen3.6-35B-A3B 的 Gated Attention 層有 16 個 Q Head。
就像同時派 16 個偵探去調查同一個案件，每個偵探關注不同的線索。最後把 16 個偵探的發現合在一起，就能得到最全面的結論。
Head Dimension 頭維度
注意力
每個注意力頭內部的向量大小。Qwen3.6-35B-A3B 的 Gated Attention 使用 head dim = 256，代表每個頭用 256 個數字來描述 Q、K、V 向量。head dim 直接影響 KV Cache 的大小。
GQA / KV Heads 分組查詢注意力
注意力
Grouped Query Attention。一種節省記憶體的注意力變體。標準注意力中，Q、K、V 的頭數相同。GQA 讓多個 Q Head 共用同一組 K 和 V Head。

Qwen3.6-35B-A3B：16 個 Q Head，但只有 2 個 KV Head。這代表 KV Cache 只需要存 2 個頭的資料（而不是 16 個），節省 8 倍記憶體。
16 個學生（Q Head）在考試，但不需要每人一本教科書（KV）——只需要 2 本共用的教科書就夠了。省書（記憶體）！
Gated DeltaNet 門控 DeltaNet（線性注意力）
注意力
Qwen3.6-35B-A3B 中佔 30/40 層的注意力機制。和標準注意力不同，它使用「Recurrent State」（循環狀態）而非 KV Cache。關鍵特性：
• 狀態大小是固定的（~2 MiB/層），不會隨 context 長度增長
• 計算複雜度是 O(n) 而非 O(n²)，處理長文本更快
• 30 層 × 2 MiB = 只佔 ~60 MiB，不管 context 是 4K 還是 262K
標準注意力像一個筆記狂——每聽到一句話就抄一整頁筆記（KV Cache），聽越多筆記越厚。DeltaNet 像一個有超強記憶力的人——不抄筆記，只在腦子裡維護一個固定大小的「總結」。不管聽了多少，腦子裡的「總結」永遠只有那麼大。
Gated Attention 門控注意力（標準注意力）
注意力
Qwen3.6-35B-A3B 中佔 10/40 層的注意力機制。和傳統 Self-Attention 類似，使用完整的 Q/K/V 計算，會產生 KV Cache。搭配 GQA（2 個 KV Head），這 10 層貢獻了模型所有的 KV Cache 開銷。

「Gated」表示加入了門控機制——讓模型自己學習「這層的結果應該保留多少」，提升訓練穩定性。
Flash Attention 閃電注意力
效能
一種讓注意力計算更快、更省記憶體的技術。標準注意力需要在記憶體中存放完整的注意力矩陣（大小 = context² × heads），Flash Attention 透過分塊計算避免這個巨大矩陣，大幅降低記憶體使用。在部署計畫中用 --flash-attn 開啟，必須啟用。
標準做法像把整張大地圖攤開在桌上一次看完（需要超大桌子）。Flash Attention 像把地圖折成小塊，一次只看一小塊，但看的順序很聰明，最終結果完全一樣，桌子卻只需要很小。
🔬 量化技術 7 個術語
Quantization 量化
核心
把模型的參數從高精度數字壓縮成低精度數字，以減少儲存空間和計算量。原始模型用 BF16（每個數字佔 16 bit = 2 bytes），量化到 Q4 就是壓縮成 4 bit = 0.5 bytes。壓縮 4 倍，代價是少量精度損失。
精度等級 每參數位元 模型大小(35B) 品質 ───────────────────────────────────────────────── BF16 (原始) 16 bit ~71 GB 100% Q8_0 8 bit ~38 GB ~99% Q6_K 6 bit ~31 GB ~97% Q5_K_M 5 bit ~26 GB ~95% Q4_K_M ⭐ 4 bit ~21 GB ~92% ← 推薦 Q3_K_S 3 bit ~14 GB ~85% Q2_K 2 bit ~13 GB ~70%
就像把高畫質照片（原圖 10MB）壓縮成 JPEG。壓縮到 2.5MB 你幾乎看不出差別（Q4），壓縮到 1MB 開始有點糊（Q2）。重點是找到「壓到多小還能接受」的平衡點。
GGUF GGML 通用檔案格式
格式
llama.cpp 專用的模型檔案格式。全名 GGML Universal File（GGML 是 llama.cpp 底層的計算引擎名稱）。一個 .gguf 檔案包含了模型的所有權重、量化參數和架構資訊。你下載的 Qwen3.6-35B-A3B-Q4_K_M.gguf 就是這種格式。
Q4_K_M, Q3_K_S, Q5_K_M… 量化等級命名
格式
GGUF 量化的命名規則：
• Q4 = 4-bit 量化（數字代表每個參數的位元數）
• K = K-quant 方法（使用超級塊結構，比舊式更好）
• M / S / XL = 大小變體。M（Medium）= 中等品質平衡；S（Small）= 更小檔案但品質更低；XL = 部分層保持更高精度

Q4_K_M 就是「4-bit K-quant 方法，中等品質平衡版」。這是社群公認的甜蜜點。
BF16 / FP16 / FP32 浮點數精度格式
精度
數字的儲存精度：
• FP32（32-bit 浮點）= 最高精度，每個數字佔 4 bytes
• FP16（16-bit 浮點）= 半精度，每個數字佔 2 bytes
• BF16（Brain Float 16）= Google 發明的特殊 16-bit 格式，範圍和 FP32 一樣大但精度略低，訓練和推理的事實標準

模型原始用 BF16 訓練（~71 GB），量化就是把 BF16 壓成 Q4（每參數 4 bit = 0.5 bytes）等更小的格式。
UD (Unsloth Dynamic) Unsloth 動態量化
進階
由 Unsloth 團隊開發的進階量化方法。不是所有層都用同樣的精度——它會分析每一層的重要程度，對重要的層（如 Router、早期 Attention 層）保持更高精度，對不重要的層用更低精度。結果是在相同檔案大小下，品質比普通量化更好。
就像修照片時，把人臉（重要部分）保留高畫質，背景（不重要部分）壓縮多一點。整張照片大小差不多，但看起來更好。
imatrix (Importance Matrix) 重要性矩陣
進階
量化時用來衡量「哪些參數比較重要」的參考資料。透過在校準資料集上做一次推理，統計每個參數對輸出的影響程度。量化時對重要的參數保留更多精度，不重要的壓縮更多。使用 imatrix 的量化版本通常品質更好。
MTP / Speculative Decoding 多 Token 預測 / 投機解碼
加速
Multi-Token Prediction。傳統模型一次只能生成 1 個 token（需要做一次完整的前向傳播）。MTP 讓模型一次預測 2-3 個 token，然後再驗證這些預測是否正確。如果預測對了，就等於一次省了好幾次前向傳播。

Qwen3.6 原生支援 MTP——模型本身就內建了預測頭，不需要額外的小模型。用 --spec-type draft-mtp 啟用，可加速 1.4–2.2 倍。
普通打字：一個字一個字敲。MTP：先猜接下來幾個字，一次打出來，然後檢查猜得對不對。猜對了就省時間（接受率 >80%），猜錯了就回頭改。對於常見的句式（「你好，請問」），猜中率極高。
💾 記憶體管理 7 個術語
VRAM 顯示記憶體 / 顯存
硬體
Video RAM，顯示卡（GPU）上的專用記憶體。RTX 3070 Ti 有 8 GB VRAM。VRAM 的速度比系統 RAM 快很多倍（~600 GB/s vs ~50 GB/s），所以把資料放在 VRAM 裡計算速度最快。但 8 GB 非常小，整個模型放不下，所以才需要各種卸載策略。
VRAM = 你辦公桌上的空間（很小但伸手就到，效率最高）。RAM = 辦公室的書架（大很多但要走幾步路去拿）。我們的目標是把最常用的東西放桌上，其他的放書架。
System RAM 系統記憶體
硬體
電腦主機板上的記憶體，你有 72 GB。比 VRAM 慢但大得多。在我們的部署方案中，所有 MoE Expert 權重都放在 RAM 中（~20 GB），由 CPU 負責計算。72 GB 非常充裕，是這次部署的秘密武器。
OOM (Out of Memory) 記憶體不足
錯誤
程式需要的記憶體超過了硬體可用量，導致崩潰。在 AI 部署中最常見的就是 VRAM OOM——模型權重 + KV Cache + 計算暫存超過了 8 GB VRAM。我們的所有優化策略本質上都是在避免 OOM。
mmap (Memory Map) 記憶體映射
記憶體
一種讓作業系統「假裝」檔案已經載入記憶體的技術。實際上只有被存取到的部分才會真正讀入 RAM。好處是啟動快（不需要一次讀完整個 21 GB 的檔案），壞處是推理過程中可能會因為「Page Fault」（還沒載入的部分被存取到）而突然卡頓。

在 Windows 上建議用 --no-mmap 關閉它，改為一次性完整載入（反正你有 72 GB RAM 夠用）。
mlock 記憶體鎖定
記憶體
告訴作業系統：「不要把這塊記憶體的資料換出去」。正常情況下，如果 RAM 不夠用，Windows 會把不常用的資料換到硬碟上（Pagefile），這叫「Swap」。但 swap 速度極慢（SSD ~5 GB/s vs RAM ~50 GB/s），會讓推理嚴重卡頓。--mlock 保證模型權重永遠留在 RAM 中。
Activation Vector / Buffer 激活向量 / 計算暫存
記憶體
模型推理過程中，每一層的計算中間結果。一個 token 經過某一層的計算後，產出的結果向量就是「Activation」。它會被傳遞給下一層作為輸入。

在 --cpu-moe 模式下，只有這個極小的 Activation Vector（~4-16 KB）會透過 PCIe 在 GPU 和 CPU 之間傳輸，而不是搬運幾 GB 的 Expert 權重。這就是為什麼 MoE 卸載可以這麼高效。
Expert Cache / LFU 專家快取 / 最低頻率淘汰
記憶體
在 GPU VRAM 中保留一小塊空間，用來快取最常被 Router 選中的「熱門 Expert」。當路由到的 Expert 剛好在快取中時，直接在 GPU 上計算（零延遲）。只有快取中沒有時，才需要走慢速的 CPU 路徑。

LFU（Least Frequently Used）= 淘汰策略。當快取滿了需要騰出空間時，淘汰使用次數最少的 Expert。用 --moe-expert-cache-size 8 設定快取 8 個 Expert。
💻 硬體相關 5 個術語
GPU 圖形處理器 / 顯示卡
硬體
Graphics Processing Unit。原本設計來畫圖形（3D 遊戲），但因為它擅長做大量平行的數學計算（矩陣乘法），被拿來跑 AI 模型。RTX 3070 Ti 雖然 VRAM 只有 8 GB，但它的計算速度（FLOPS）仍然比 CPU 快幾十倍。
CPU 像一個超級聰明但只有一隻手的人（一次只做一件事但做得很精確）。GPU 像一群普通人有幾千隻手（每隻手只能做簡單的加減乘除，但同時做幾千個）。AI 推理恰好需要做大量簡單的乘法，所以 GPU 完勝。
PCIe (PCI Express) 匯流排
硬體
連接 GPU 和 CPU/RAM 之間的「高速公路」。RTX 3070 Ti 使用 PCIe 4.0 x16，理論頻寬 ~32 GB/s，實際約 25 GB/s。在 MoE 卸載中，PCIe 並非瓶頸——因為只傳輸極小的 Activation Vector，不是搬運整個 Expert 權重。
GPU 和 CPU 分別在城市的兩端。PCIe 就是連接它們的高速公路。我們的策略不是把整棟大樓搬過去（搬 Expert 權重），而是只用快遞寄一封信（Activation Vector），所以高速公路完全不會塞車。
Compute Capability 計算能力版本
硬體
NVIDIA GPU 的「世代代碼」。決定了 GPU 支援哪些計算功能。RTX 3070 Ti 的 Compute Capability 是 8.6（Ampere 架構）。編譯 llama.cpp 時需要告訴 CMake 這個數字（-DCMAKE_CUDA_ARCHITECTURES=86），這樣編譯器才能生成最適合這張卡的機器碼。
NVMe SSD 固態硬碟
硬體
模型 GGUF 檔案存放的地方。NVMe SSD 的讀取速度約 5-7 GB/s，模型啟動時會從 SSD 載入到 RAM。21 GB 的模型檔案大約 3-4 秒就能讀完。比傳統硬碟（~150 MB/s）快 30-40 倍。
Memory Bandwidth 記憶體頻寬
硬體
記憶體每秒能傳輸多少資料。LLM 推理（尤其是 token 生成階段）主要受限於記憶體頻寬而非算力。RTX 3070 Ti 的 VRAM 頻寬 ~600 GB/s，系統 RAM（DDR4）約 ~40-50 GB/s。RAM 頻寬是 MoE CPU 卸載時的實際瓶頸。
頻寬就像水管的粗細。VRAM 是粗水管（每秒 600 升），RAM 是細水管（每秒 50 升）。Expert 在 CPU/RAM 計算時，資料流過的是細水管，所以速度會比全放 GPU 慢。
⚙️ llama.cpp 參數 8 個術語
llama.cpp 推理引擎
工具
用 C/C++ 寫的開源 LLM 推理引擎。由 Georgi Gerganov 開發。它可以在各種硬體上運行 GGUF 格式的模型——從手機到伺服器都行。是目前社群最流行的本地端 LLM 推理方案，特別擅長在消費級硬體上跑大模型。
-ngl / --n-gpu-layers GPU 層數
參數
指定要把多少層放到 GPU 上計算。設為 99（或任何超過實際層數的值）= 盡可能多的層放 GPU。搭配 --cpu-moe 使用時，它指的是「Dense 部分」的層數。
--cpu-moe / --n-cpu-moe MoE 專家卸載至 CPU
核心參數
這次部署最關鍵的參數！告訴 llama.cpp：「把 MoE 的 Expert FFN 權重放在 CPU RAM，不要佔 GPU VRAM」。
• --cpu-moe = 所有層的 Expert 都放 CPU
• --n-cpu-moe 35 = 前 35 層的 Expert 放 CPU（其餘留 GPU）

這讓 8 GB VRAM 只需要裝 Dense 層（~2-3 GB），剩餘空間留給 KV Cache 和計算暫存。
--cache-type-k / --cache-type-v KV Cache 量化類型
參數
控制 KV Cache 的儲存精度。可選 f16（最高品質）、q8_0（減半大小）、q4_0（四分之一大小）。我們推薦 q8_0：品質幾乎無損，記憶體減半。在極長上下文（262K）下可用 q4_0 進一步壓縮。
-b / -ub (Batch Size) 批次大小 / 微批次大小
參數
-b (batch size)：處理你輸入的 prompt 時，一次處理多少 token。-ub (ubatch size)：每次實際送進 GPU kernel 的 token 數。

-b 2048 代表一次讀取 2048 個 prompt token，-ub 512 代表分 4 次送進 GPU（每次 512 個）。ub 越小，VRAM 峰值越低但速度越慢。VRAM 緊張時可調低 ub。
你要搬 2048 本書（prompt tokens）進房間（GPU）。-b=2048 是總共要搬的量，-ub=512 是每趟搬幾本。每趟搬少一點（512），佔用的搬運空間（VRAM）就少一點。
-c / --ctx-size 上下文大小
參數
設定這次會話允許的最大 token 數。-c 32768 = 最多 32K tokens。這個值直接決定 KV Cache 要分配多少記憶體。設太大會 OOM，設太小會限制模型能「記住」的對話長度。建議從 32K 開始，按需調整。
-t / --threads CPU 執行緒數
參數
CPU 用多少個線程來做計算。應設為 CPU 的物理核心數（不是邏輯線程數 / 超線程數）。例如 8 核 16 線程的 CPU，設 -t 8。設太多反而會因為線程搶資源而變慢。
--cont-batching 連續批次處理
參數
Server 模式下，讓多個使用者的請求在同一時間共用 GPU 計算。不開的話，一次只能服務一個使用者；開了之後，可以把多個使用者的 token 合併成一個批次一起處理，提高 GPU 利用率。
📈 效能指標 4 個術語
Tokens per Second (t/s) 每秒 Token 數
效能
衡量模型回覆速度的核心指標。每秒能生成幾個 token。人類閱讀速度約 3–5 t/s，所以 >10 t/s 就能做到即時對話。我們的目標是在 32K context 下達到 30–60 t/s。
Prompt Processing / Prefill 提示處理 / 預填充
效能
推理的第一階段：讀取並理解你輸入的所有文字。這個階段可以平行處理（一次算很多 token），所以速度受 batch size 和 GPU 算力影響。對長 prompt（如整篇文章），預填充可能需要幾秒到幾十秒。
Token Generation / Decode Token 生成 / 解碼
效能
推理的第二階段：一個一個生成回覆的 token。這個階段是串行的（下一個 token 依賴上一個 token 的結果），速度主要受記憶體頻寬限制。這就是我們衡量 t/s 的階段。MTP 就是在這個階段做加速的。
Throughput / Latency 吞吐量 / 延遲
效能
Throughput（吞吐量）= 單位時間內能處理多少工作量（如 tokens/s）。
Latency（延遲）= 從送出請求到收到第一個回覆的等待時間。

兩者通常是互相拉扯的：追求高吞吐量（合併多個請求）會增加單個請求的延遲。在單用戶場景下，我們優先追求低延遲。
🎲 取樣與生成 4 個術語
Temperature 溫度
取樣
控制模型回答的隨機程度。
• 溫度 = 0：完全確定性，永遠選機率最高的 token（像考試答標準答案）
• 溫度 = 0.6（推薦）：適度隨機，回答自然且有變化
• 溫度 = 1.0+：高度隨機，更有創意但可能胡說
點菜時：溫度=0 永遠點招牌菜；溫度=0.6 通常點喜歡的但偶爾嘗鮮；溫度=1.5 亂點一通，可能發現新大陸也可能踩雷。
Top-p (Nucleus Sampling) 核取樣
取樣
只從「機率加總到 p」的候選 token 中選擇。top-p 0.95 = 把所有 token 按機率從高到低排，只保留加總到 95% 的那些候選者，丟棄剩下的 5% 長尾（極不可能的 token）。這比固定的 top-k 更靈活——當模型很確定時候選者少，不確定時候選者多。

取樣
只保留機率最高的前 K 個候選 token，丟棄其餘。top-k 20 = 只從排名前 20 的 token 中選一個。常和 top-p 搭配使用。

📊 MTP 投機窗口長度對 TPS 的影響 (Spec-Window vs. TPS)
投機黃金甜蜜點
實測證實，當 spec_draft_n_max = 2 (投機 2 個 Token) 時速度最快。將其拉大到 3 或 4 時，速度反而大幅下降。
原原理剖析：35B 模型的草稿接受率在本地量化下約為 70%~77%。如果將投機窗口設為 4，雖然一次可能多產出 Token，但由於接受率不足導致頻繁觸發昂貴的「回退重算開銷 (Verification Fallback)」，多餘的驗證時間直接抵消了投機優勢。因此 2 是本機 MTP 部署的絕對黃金甜蜜點。
⚔️ 混合推理模式與 CPU 算力牆突破 (CPU Bound vs. GPU Offload)
算力牆與 GPU 卸載真相
雙通道解鎖後，記憶體複製頻寬提升了 **133.8%** (唯讀頻寬大增 454.9%)，但我們發現 3-bit 模型（Q3_K_M）的純 CPU 專家推理速度受限於 CPU 反量化算力瓶頸，未能完全釋放記憶體頻寬！
核心發現 — CPU 算力牆 (CPU Bound)：這是因為 3-bit 量化的解碼演算法更為複雜，CPU 在進行 AVX2/FMA 反量化（De-quantization） 時的運算延遲，已經完全蓋過了因為模型體積變小而節省的記憶體傳輸時間。此時限制速度的不再是「頻寬」，而是「CPU 的 FMA 算力」！
最佳化突破：我們精密壓榨 8GB 顯存空間，進行了 GPU 專家卸載（-ncmoe）網格搜尋。實測發現，將部分 MoE 專家卸載至 GPU（-ncmoe 35），能完美利用 GPU Tensor Cores 的強大矩陣算力抹平反量化開銷，成功打破 CPU 算力牆，使 Q4 滿血速度攀升至歷史最高的前台 **35.02 TPS**，Q3 達到 **30.65 TPS**！
